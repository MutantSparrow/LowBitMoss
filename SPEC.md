# moss_lowbit_v1: file format and loader requirements


## Evaluation scope and corrected interpretation

All totals here are model-file sizes, not peak RAM or VRAM. The 7.18 GB small package has automatic scores (local HPS 11.06) and an informal web-interface test, but no complete-package judge pass. The proposed 7.97 GB quality package is unmeasured as that exact encoder/decoder combination. A 4.27 and 23/24 accepted belong to mixG_tuned_t with the bf16 encoder and full VAE (22.58 GB of files); A 4.06 and 18/24 belong to tmixG_x with those components (21.78 GB). See paper Table I7 for exact configurations, including non-distilled tests made with the full VAE.

Scores use a local HPSv3-based implementation, not yet validated for numerical parity with official HPSv3. Interpret each paired difference using its own interval; no global noise cutoff or quality-equivalence claim is used. Judge ±0.2 is an informal spread estimate, not a confidence interval. Corrected comparisons and charts are generated by `scripts/review_reporting.py` (paper Tables I8-I9).

mixI changes 1-bit attention and 1-bit FFN-down together, so only that combined allocation is shown to fail. mixH2 increases both distinct samples and optimizer steps; a data-only gain is not isolated. mixG_tuned has all six text prompts exact and five balloons correct, but the six-fruit prompt is wrong (five fruits, like the teacher). The six-seed kitchen comparison (4/6 versus 1/6, one shared failure) is suggestive: exact two-sided paired p = 0.25, not an established kitchen-specific effect.

Common-preprocessing measurements on primary 1024 px images resized to 768 give edge-energy changes of -21.3% for tmixG_x, -9.9% for tmixG_tuned, and -0.3% for the folded mixG_tuned_t, against the distilled teacher. These are Laplacian RMS changes, not percentages of meaningful detail retained. The earlier 35% and 17% summaries came from native 768 px runs and must not be transferred to the 1024 px package. Similar mean edge energy does not establish losslessness. Encoder/VAE swaps were not isolated as having zero additional softness.

Folded corrections are stored as bf16 factors, multiplied/accumulated in fp32, and the reconstructed weight is rounded to the compute dtype. They are not exact copies of the original fp32 delta. No wall-clock speedup is measured.


A quantized MOSS-Image SFT diffusion transformer stored as one `.safetensors` file. The format follows the idea of the PrismML
Bonsai-Image whitepaper (group-wise symmetric low-bit weights with fp16 group scales, small sensitive tensors kept in bf16); the exact
layout below is this project's own. Reference implementation: `scripts/lowbit_pack.py` (pack/unpack/dequantize) and
`custom_nodes/ComfyUI-MOSS-LowBit/lowbit.py` (ComfyUI loader).

The teacher model (`moss_image_sft_bf16.safetensors`, 5.08B parameters, 42 blocks) has per block `layers.N.proj.{qkv,o,ffn_up_gate,ffn_down}.weight`
(bias-free) = 94% of the parameters; everything else (`shared_block_modulation`, `video_head_modulation`, `time_embedding`, `video_embedder`,
`final_linear_video`, `text_embedder.*`, norms) is small and stays bf16 unless quantized explicitly.

## Quantized linears

For each quantized linear X (the 4 matrices of any of the 42 blocks, optionally any other `nn.Linear` such as `text_embedder.*`):

    X.weight        uint8   [out, in*bits//8]  packed codes (bits per code from the kind; element j of a byte at bit j*bits, LSB first)
    X.weight_scale  float16 [out, in//128]     group size 128 along `in` (`in` must be a multiple of 128)
    X.weight_kind   uint8   scalar             1=bin, 2=tern, 3=int2, 4=int4, 5=tern5, 6=int3
    X.lora_a        bf16    [r, in]            optional low-rank correction (or float8_e4m3fn, see "Compact LoRA")
    X.lora_b        bf16    [out, r]           optional low-rank correction (or float8_e4m3fn, see "Compact LoRA")
    X.lora_a_scale  float16 scalar             only next to a float8_e4m3fn X.lora_a
    X.lora_b_scale  float16 scalar             only next to a float8_e4m3fn X.lora_b
    X.bias                                     stays bf16 under its normal name, if the linear has one

Dequantization: `w = (code - offset[kind]) * scale[:, group]` (+ `lora_b @ lora_a` if present, so `W = Q + B A`).

| kind | name | bits/code | code values | offset | weight levels (times scale) | bits/weight incl. scales |
|---|---|---|---|---|---|---|
| 1 | bin | 1 | 0, 1 | 0.5 | -0.5, +0.5 | 1.125 |
| 2 | tern | 2 (slot) | 0, 1, 2 | 1 | -1, 0, +1 | 2.125 |
| 3 | int2 | 2 | 0..3 | 1.5 | -1.5 .. +1.5 | 2.125 |
| 4 | int4 | 4 | 0..15 | 7.5 | -7.5 .. +7.5 | 4.125 |
| 5 | tern5 | 1.6 | 0, 1, 2 | 1 | -1, 0, +1 | 1.725 |
| 6 | int3 | 3 | 0..7 | 3.5 | -3.5 .. +3.5 | 3.125 |

Nothing else is required: no `X.comfy_quant` keys and no file metadata (the writers add `{"moss_lowbit_v1": "1"}` as a marker, readers ignore it).
Every other tensor keeps its original name and dtype (bf16). A linear without `X.weight_kind` is loaded as a plain bf16 linear; kinds can differ per layer.
`X.weight` keeps the original name so ComfyUI's model detection (`shared_block_modulation.weight`, `layers.0.proj.ffn_up_gate.weight`.shape[0],
`layers.0.proj.qkv.weight`) is unchanged; detection only reads shape[0], which the packing does not touch.

Dequantization in the loader is bit-identical to `lowbit_pack.dequantize`: fp32 `(code - offset) * scale`, one rounding to bf16.

## Kind 5 (tern5): ternary codes, 5 per byte

Same codes as kind 2 (code 0, 1, 2 = weight -1, 0, +1, offset 1, fp16 scales `[out, in//128]` unchanged), but 5 codes per byte in base 3
instead of 4 per byte in 2-bit slots: `byte = sum_{j=0..4} code_j * 3^j` (value 0..242, first code in the lowest digit), packed along `in` per
row. Rows are padded with code 1 (weight 0) to a multiple of 5, so `X.weight` is uint8 `[out, ceil(in / 5)]` (in=3072 -> 615 bytes,
in=8192 -> 1639). That is 1.6 bits/code instead of 2 (-20% on the packed codes). The loader derives the expected width as `ceil(in / 5)` and
rejects any other width; `lowbit_pack.packed_cols(in, kind)` gives the width of any kind. In `lowbit_pack`, `KINDS[5][1]` (= 1.6) is the `bits`
argument that selects this packing in `pack_codes` / `unpack_codes`; `unpack_codes(packed, bits, n)` takes `n` to drop the padding. A
ternary-trained layer is exported as kind 5 by setting `qlayer.EXPORT_TERN5 = True` (`train_blocks.py --tern5`); a file may mix kinds 2 and 5.

## Kind 6 (int3): 3-bit codes, 8 per 3 bytes

8-level symmetric codes 0..7 (`w = (code - 3.5) * scale`). 8 consecutive codes along `in` form one little-endian 24-bit word, code j at bit
offset 3*j (`word = sum_j code_j << 3j`), stored as 3 bytes (`word & 255`, `word >> 8 & 255`, `word >> 16`). `in` is a multiple of 128, so
there is no padding: `X.weight` is uint8 `[out, in*3//8]` (in=3072 -> 1152 bytes, in=8192 -> 3072). Relative weight MSE with optimal group
scales on `layers.20.proj.ffn_up_gate.weight` of the teacher: int4 0.0107, int3 0.0377, int2 0.122. The loader derives the expected width
`in*3//8` and rejects any other; a kind-6 linear takes `lora_a`/`lora_b` like every kind. The loader layout's `quantize()` (plain rounding, used
by the tests only) uses 0.75 * absmean scales for int3. Tests: `scripts/test_int3.py` (CPU only).

## Compact LoRA: float8_e4m3fn factors with a per-tensor scale

The low-rank correction of a quantized linear (`W = Q + B A`, normally bf16 `X.lora_a` `[r, in]` and `X.lora_b` `[out, r]`) may be stored compactly: both
factors as float8_e4m3fn, each with a scalar (0-dim) fp16 tensor `X.lora_a_scale` / `X.lora_b_scale`; the effective factor is `lora.float() * scale`.
The scale is `amax(|factor|) / 448` (448 = largest finite e4m3fn value), rounded UP to an fp16 so that nothing overflows (e4m3fn has no inf, 464 and
above becomes NaN); no further headroom is needed because the error is flat for `amax / scale` anywhere in 14..448. Measured on mixH2_x (270 factors,
rank 32/64): relative error of a factor `||fp8 - orig|| / ||orig||` 1.7-2.7%, of `B A` 3.7%, of the whole weight `Q + B A` 0.1-0.5%, and the weight error
against the teacher changes by <= 2e-5 (0.36171 -> 0.36172 on `layers.33.proj.ffn_up_gate`); LoRA bytes 203.7 -> 101.8 MB (file 1.951 -> 1.850 GB).

Rules: a float8_e4m3fn factor needs its scale; a factor of any other dtype must not have one and loads as before (cast to the compute dtype); a scale
without its factor or a non-scalar scale is a `ValueError`; each factor stands alone (an fp8 `lora_a` with a bf16 `lora_b` is legal).
`lowbit_pack.lora_to_fp8(t) -> (fp8, scale)` and `lowbit_pack.lora_from_stored(t, scale=None, dtype=float32)` convert (`None` stays `None`);
`scripts/compact_lora.py --inp X --out Y` rewrites a whole file and reports sizes and errors. The loader keeps the fp8 factors and their scales in the
layout params (all four are tensor fields, so `to_device` / `clone` / `copy_from` / gathered buffers carry them, and the factors take half the VRAM too)
and applies the scales inside `dequantize_packed`, where the LoRA fold stays. An older loader would cast the fp8 factors to bf16 WITHOUT the scales (wrong
weights, only an "unexpected keys" warning), so compact files need the current pack and a ComfyUI restart. Anything else that reads `lora_a` / `lora_b`
of a file must go through `lora_from_stored` (`e2e_tune.py`), and anything that drops a linear's keys must drop the two scale keys (`make_hybrid.py`).
`e2e_tune.py` writes its tuned factors as plain bf16 again: run `compact_lora.py` on the result. Tests: `scripts/test_lora_fp8.py` (CPU only).

## ComfyUI loader requirements

Load with the node "MOSS LowBit UNET Loader" (`custom_nodes/ComfyUI-MOSS-LowBit`), not the stock UNETLoader: ComfyUI core only loads quantized
layers that have a hard-coded branch in `comfy/ops.py`, so the pack passes its own `custom_operations`. The node registers a
`QuantizedTensor` layout (`MossLowBitLayout`); the packed codes and scales stay resident and the bf16 weight only exists inside the linear call.
The low-rank term is folded into the layout's `dequantize()` (`W = Q + B A`), which every code path uses (`F.linear(x, QuantizedTensor)` decomposes
before it reaches a registered `aten.linear` handler, so a LoRA branch hooked into that handler is silently skipped).

ComfyUI LoRA patches are refused on these weights. When ComfyUI applies a LoRA to a quantized weight (and again whenever it faults a patched weight back in
under dynamic VRAM) it re-encodes the result through the layout's `requantize_kwargs()` / `quantize()`. That is plain absmean rounding: the trained group
scales and the low-rank branch are lost, and which linears are hit depends on VRAM residency (a 4-step test with the turbo LoRA on top of quantized files
gave a bimodal result, half of the images collapsed). `requantize_kwargs()` therefore raises `NotImplementedError`. To use a LoRA, fold it into the file as
extra low-rank factors (`scripts/add_turbo_factors.py`, `W = Q + B A + dW`, applied in fp32 inside the dequantization).
